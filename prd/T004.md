# T004 — Task materialization, audit, and provenance

## Metadata

- Last specification update: 2026-09-12

## Objective

Close the information loop by turning formally accepted `NEW_TASK` proposals into canonical Scalable Ralph tasks and by exposing auditable history/contribution queries without adding semantic controller behavior.

## Scope

### In scope

- mechanical proposal consolidation;
- deterministic task-ID allocation;
- root PRD task-index insertion;
- creation of macro-task specification and Progress files;
- non-NEW_TASK acceptance with explicit canonical-distillation reminder;
- event history filtering;
- per-agent contribution history;
- consistency checks for the Blackboard memory structure.

### Out of scope

- semantic application of arbitrary accepted architecture/requirement text;
- automated Git commits;
- graph database or provenance index.

## Contracts and interfaces

`bb consolidate Pxxxx` validates only formal consensus. For `NEW_TASK`, it materializes the proposal deterministically. For other proposal kinds, it marks the proposal accepted and records that an agent must distill the accepted decision into the appropriate canonical file.

Stable task IDs are allocated from a persistent monotonic counter and never intentionally reused.

## Sub-tasks

### T004-SUB001 — Implement proposal consolidation

- Goal: accept formally ready proposals without semantic judgment.
- Dependencies: —
- Acceptance criteria:
  - Not-ready proposal cannot consolidate.
  - Accepted proposal becomes immutable to new stances/amendments.
  - Consolidation is atomic under `flock`.
- Verification:
  - Automated tests in T005.

### T004-SUB002 — Materialize NEW_TASK proposals

- Goal: create canonical task spec, Progress, and root PRD row from accepted task proposal metadata.
- Dependencies: T004-SUB001
- Acceptance criteria:
  - New stable Txxx ID allocated.
  - Root index, task spec, and progress all agree.
  - Dependencies must reference existing tasks.
- Verification:
  - Automated tests in T005.

### T004-SUB003 — Expose audit/provenance

- Goal: inspect event history and agent contribution traces.
- Dependencies: T004-SUB001
- Acceptance criteria:
  - History can filter by any stable task/proposal/note/objection reference.
  - Contributions can filter by agent.
  - Consistency checker detects missing/mismatched canonical task state.
- Verification:
  - Automated tests in T005.

## Risks

- A persistent event log can dirty a shared Git working tree; MVP leaves commit/checkpoint policy to the pilot rather than auto-committing coordination state.

## Open questions
