# T006 — Second-pass hardening and lifecycle correctness

## Metadata

- Last specification update: 2026-09-12

## Objective

Perform an adversarial second-pass review of the Blackboard MVP and fix correctness or usability defects that could invalidate Pilot 0 observations.

## Scope

### In scope

- proposal revision/re-review semantics;
- proposal withdrawal/supersession lifecycle;
- accepted non-`NEW_TASK` distillation tracking;
- CLI identity ergonomics and instruction/CLI consistency;
- human-readable state synchronization where machine state changes;
- stronger validation and consistency checks;
- regression tests for all fixes.

### Out of scope

- semantic duplicate-proposal detection;
- source-file leases/worktree isolation;
- agent wake-up/watchers;
- changing the fixed consensus threshold before pilot evidence.

## Context

A second review after v0.1.0 found that the happy-path tests were green but several lifecycle edge cases could distort the information loops measured by the pilot. These must be corrected before multi-agent execution.

## Sub-tasks

### T006-SUB001 — Adversarial design/code review

- Goal: identify correctness gaps that affect coordination, deliberation, provenance, or agent usability.
- Dependencies: —
- Acceptance criteria:
  - Findings are preserved in a report.
  - Each finding is classified as fix-now or pilot-observe.
- Verification:
  - Review CLI behavior, proposal lifecycle, note lifecycle, claim lifecycle, and audit/provenance paths.

### T006-SUB002 — Harden proposal and note lifecycle

- Goal: prevent stale consensus and incomplete proposal lifecycle from producing false acceptance or dead-end information.
- Dependencies: T006-SUB001
- Acceptance criteria:
  - Material amendments require fresh reviewer stances.
  - `NEW_TASK` structured revisions can update the materialized task specification.
  - Open proposals can be withdrawn and accepted alternatives can supersede stale proposals.
  - Accepted non-`NEW_TASK` proposals expose pending canonical distillation and can be marked distilled with provenance.
  - Human-readable Markdown status is synchronized when note/proposal state changes.
- Verification:
  - Unit tests cover each lifecycle transition.

### T006-SUB003 — Harden CLI and validation

- Goal: ensure agents can execute the skill literally and invalid coordination state is rejected early.
- Dependencies: T006-SUB001
- Acceptance criteria:
  - `--agent` works both before and after a subcommand.
  - Duplicate/contradictory CLI output is removed.
  - Core validation rejects invalid task priorities/dependency identifiers.
  - Completion provenance does not misattribute the repository HEAD as the completing agent's commit.
  - Consistency checks cover live claims and proposal artifacts.
- Verification:
  - CLI regression tests and repository consistency pass.

### T006-SUB004 — Final regression and packaging

- Goal: ship a verified v0.1.1 repository with complete Git history.
- Dependencies: T006-SUB002, T006-SUB003
- Acceptance criteria:
  - Full test suite passes.
  - `bb check` passes.
  - Working tree is clean after commit.
  - ZIP contains `.git` and can be extracted with history intact.
- Verification:
  - Run tests, CLI smoke tests, `bb check`, ZIP extraction, and `git log` from extracted archive.

## Risks

- Over-hardening before the pilot could hide behaviors that should instead be measured empirically.
- Adding lifecycle states without clear semantics could make the MVP unnecessarily complex.

## Open questions

- None. Keep changes limited to correctness and instruction/implementation alignment.
